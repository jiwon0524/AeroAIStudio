# Gazebo integration V0.6

## 검증 상태

현재 Windows: gz/ROS2/ros_gz 없음, 읽기 전용 WSL distro 조회 결과 없음. **Actual Gazebo launch/closed loop: NOT VERIFIED.** Unit fixture는 실제 runtime 검증이 아닙니다. tools/closed_loop_smoke.py는 미설치 시 NOT VERIFIED JSON을 저장하며 대체 simulator를 만들지 않습니다.

## 책임과 실제 연결

- process_manager.py: 전용 GZ_PARTITION, GUI 또는 `gz sim -s --headless-rendering`, paused startup, own PID/process-group shutdown/log.
- transport.py: lazy native gz.transport13/gz.msgs10, bounded request/response, LaserScan/stats subscriptions, Condition 기반 fresh timestamp wait. Qt/UI import에서 Linux 패키지를 import하지 않습니다.
- stepping.py: /world/<name>/control의 WorldControl pause/multi_step. Physics dt0.001, action dt0.1 기본값. wall-clock sleep으로 simulation 진행을 대체하지 않습니다. sample sim_time barrier로 완료를 확인합니다. real_time_factor service도 adapter 안에 있습니다.
- entity_controller.py: Scene service의 실제 모델 pose 조회, optional EntityFactory spawn, set_pose reset/action/hold. Box entity는 SDF에 포함되어 있고 spawn_agent는 존재를 확인합니다.
- sensor_provider.py: real GPU LiDAR LaserScan4개 cardinal rays→CanonicalSensorObservation. finite range·길이4·timestamp freshness 검사, timeout이면 오류. camera는 optional None, pointcloud 미구현.
- environment.py: reset/step/observation/state/metrics/render/close. 같은 Trainer/Evaluator가 factory 주입으로 사용합니다. agent 이동 후 actual pose를 확인하며 명령 pose를 센서값으로 위장하지 않습니다.
- world_generator.py: closed_loop=True일 때 Sensors system과4-ray LiDAR가 있는 box entity를 생성합니다. legacy default export는 이전3-plugin 구조를 유지합니다. UI export/Environment launch는 closed-loop world를 사용합니다.

세계grid(x,y)→Gazebo(x+.5,y+.5), +y는 Grid의 아래쪽입니다. Agent yaw0을 유지하며 up/down/left/right는 world축 이동입니다. forward/backward는 up/down alias이고 STOP은 현 위치 hold입니다. step_size 기본1m/action, dt0.1s, goal radius0.45m. 실제 비행이나 차동구동 dynamics는 아닙니다.

## Closed loop

launch paused → wait scene+expected agent → reset entity poses → fixed step → actual pose+fresh LiDAR → model observation → proposed action → optional Safety → set_pose → fixed step → actual new pose+fresh scan → reward/done. Episode는 timestamp/pose/observations/scores/proposed/Safety/final/reward components를 기존 로그 형식에 저장합니다. Trajectory는 pose의2D projection을 사용합니다.

Goal은 실제 XY 거리≤radius. Collision은 pre-command ray clearance와 이동 길이, 실제 sensed pose의 경계·dynamic entity 근접으로 판정합니다. 이는 **kinematic/geometric collision approximation**이며 Gazebo contact sensor/rigid-body dynamics 검증이 아닙니다. 미리 알려진 객체 pose는 debug에만 기록하고 동적 LiDAR 인식 결과로 가장하지 않습니다.

Reset은 entity pose와 episode state를 되돌리며 global simulation clock은 단조 증가시켜 stale sample을 구분합니다. Domain randomization은 Gazebo goal position을 지원합니다. Dynamic entities는 Environment가 kinematic set_pose로 움직이며 복잡한 충돌반응/회피는 없습니다. Obstacle-size/light randomization은 미구현입니다.

## Ubuntu 실행

`scripts/setup_ubuntu_sim.sh`는 안내만 출력하고 sudo/apt를 실행하지 않습니다. 공식 Harmonic repository 설정을 먼저 검토한 뒤 gz-harmonic/python3-gz-transport13/python3-gz-msgs10을 설치합니다. apt native bindings와 맞는 Ubuntu system Python을 사용하세요.

```text
python3 -m venv --system-site-packages .venv
.venv/bin/python -m pip install -e ".[dev,dqn]"
.venv/bin/python scripts/check_sim_environment.py
.venv/bin/python tools/closed_loop_smoke.py --output ./work/real-gazebo
AERO_GAZEBO_INTEGRATION=1 .venv/bin/python -m pytest tests/test_gazebo_integration.py -v
```

GUI 확인은 smoke에 `--gui`를 추가합니다. Headless도 GPU LiDAR 렌더링에 Ogre2/EGL 또는 지원되는 display 환경이 필요합니다. Loop smoke는 world loaded/entity/sensor update/move/goal/collision/reset/shutdown을 체크하고 실패 원인을 JSON에 남깁니다. Process alive가 GUI render verified를 뜻하지 않습니다. 현재 report의 render_verified는 false입니다.

확인한 API 기준: [Harmonic Transport Python request/subscribe](https://gazebosim.org/api/transport/13/python.html), [world control/stepping](https://gazebosim.org/api/sim/9/pause_run_simulation.html), [Harmonic sensors](https://gazebosim.org/docs/harmonic/sensors/), [entity services](https://gazebosim.org/api/sim/9/entity_creation.html). 사용 타깃은 Harmonic이며 다른 버전의 문서와 ABI 일치는 Ubuntu에서 별도로 검증해야 합니다.
