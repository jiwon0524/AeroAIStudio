# 개발 기록과 자동 체크포인트 게시 규칙

사용자 승인: 검증 가능한 단계가 끝날 때마다 아래 절차에 따라 기록을 남기고 자동 commit/push한다. 조건을 만족하면 매번 별도 게시 요청을 기다리지 않는다. 자동화 주체는 작업 중인 에이전트이며, 상시 실행 daemon·파일 감시·Git hook는 설치하지 않는다.

## 게시 시점

|시점|기록과 게시 대상|확인할 사항|
|---|---|---|
|구현·수정과 관련 테스트 완료|검증된 코드, 테스트, 결과 요약|검증한 범위와 통과 결과를 명시|
|실험·조사 한 단계 종료|분석 보고서, 가설별 판단, 증거 경로·해시|SUPPORTED/CONTRADICTED/UNRESOLVED 및 관측·추정 구분|
|실패 원인 또는 차단 조건 확인|실패 내용, 검증된 원인·수정 근거, 미해결 사항|실패 로그 원본 보존. 원인이 불명확하면 그대로 UNRESOLVED/BLOCKED로 기록|
|계정·기기·세션 변경 전|최신 handoff와 필요한 진행 기록, 검증이 끝난 변경 부분|미완료 범위와 실행 중 작업을 명시. 계정 전환이나 프로세스 종료를 자동 수행하지 않음|
|프로젝트·주요 마일스톤 최종 완료|통합 목차, 최종 보고서, 검증·재현 방법|과거 실패를 삭제하지 않고 최종 성공과 구분|

실패 기록을 게시하는 데 코드 전체가 성공할 필요는 없다. 실패 사실과 분석 근거를 확인한 문서만 게시할 수 있다. 미완료 작업은 PARTIAL/WIP로 표시하되, 검증되지 않은 코드를 자동 게시하지 않는다. 일부 검증만 끝났다면 검증된 부분과 문서만 선택하고 나머지 코드는 로컬에 보존한다.

이 규칙은 실험·빌드·테스트 실행 권한을 확대하지 않는다. 금지된 Gazebo/World::step/Stage B 실행으로 게시 조건을 충족시키려 하지 않는다. Runtime 미검증 결과는 NOT_RUNTIME_VERIFIED로 유지한다.

## 문서 역할과 갱신

- `AGENTS.md`: 프로젝트 작업 제한과 이 게시 절차의 진입점.
- `handoff.md`: 현재 목표·범위·제한, 완료 증거, 변경 파일, 테스트, 미해결 문제, 실행 중 작업, 다음 최소 작업. `context-handoff` 절차를 따른다.
- `progress.md`: 현재 단계에 이미 있으면 짧은 진행 요약을 갱신한다. 종료된 이전 단계의 progress를 최신 상태로 덮어쓰거나 동일 목적의 진행 로그를 중복 생성하지 않는다.
- 최종 보고서와 실패 분석: 해당 단계의 원본 결과를 유지한다. 후속 정정은 별도 문서나 명시적인 정정 기록으로 남긴다.
- 상세 로그·대용량 증거는 원본 경로와 필요시 해시로 연결한다. Git 게시가 ignored/untracked 원본 전체의 백업을 대신하지 않는다. `/tmp` 등 임시 위치의 원본은 영구 보관 여부를 인계문에 기록한다.

## 저장소·브랜치 경계

- Aero 게시 대상: `origin`이 가리키는 `jiwon0524/AeroAIStudio`, 현재 승인 브랜치 `experiment/dart-internal-trace`.
- **main 직접 commit/push·병합 및 force push 금지.** 다른 브랜치가 필요하면 작업 범위에 맞는 승인을 먼저 확인한다.
- main에 기존 변경이 있으면 보존하고 승인된 별도 worktree에서 작업한다. 규칙을 이유로 다른 작업의 파일을 이동·stash·삭제·초기화·commit하지 않는다.
- 공통 스킬 변경은 프로젝트 밖 `my-agent-skills` 저장소의 파일만 그 저장소 정책에 따라 게시한다. Aero 코드·보고서·진행 기록을 공통 스킬 저장소로 복사하지 않는다.
- 자동화는 현재 저장소의 승인된 브랜치에만 적용한다. `context-handoff` 호출만으로 다른 저장소에 게시 권한이 생기지 않는다.

## 자동 게시 절차

1. 현재 작업 범위·지침·브랜치·remote와 Git 상태를 확인하고, 기존 staged/dirty 파일의 소유를 구분한다. 다른 작업의 staging이 섞여 있으면 임의로 정리하지 말고 게시를 중단한다.
2. 허용된 관련 검증을 마친다. 과거 결과는 재실행한 것처럼 표시하지 않는다. 문서만 바뀌면 링크·내용·diff 확인 등 그 변경에 맞는 검증을 사용한다.
3. 인계문과 현재 단계 기록을 갱신한다. 실패·미완료·미검증 상태도 사실대로 남긴다. 중요한 원본 로그와 기존 evidence는 보존한다.
4. 게시할 **파일 경로를 명시적으로 선택**한다. `git add .`나 validation 전체 추가를 하지 않는다. ignore된 경량 보고서가 필요하면 검토한 정확한 파일에만 `git add -f -- <path>`를 사용한다.
5. `git status`, `git diff --cached --name-only`, `git diff --cached --check`, `git diff --cached`로 실제 게시 내용을 확인한다. 비밀 정보, 다른 작업의 변경, 바이너리·빌드·캐시·가상환경·외부 패키지·불필요한 중간 산출물을 제외한다.
6. 결과가 설명되는 체크포인트 commit을 만들고 승인된 실험 브랜치로 push한다. 예: `git push origin HEAD:refs/heads/experiment/dart-internal-trace`. 검증 범위와 실패/미완료 상태를 commit 설명이나 관련 문서에 남긴다.
7. push 성공 및 원격 commit을 확인한다. commit hash·대상 브랜치·결과는 로컬 게시 영수증 또는 인계 기록에 남긴다. **자동 push 완료라고 보고하려면 실제 원격 일치까지 확인해야 한다.**

handoff를 함께 commit할 때 그 안의 Git snapshot은 저장 직전 관측값이다. 저장 commit 자체로 HEAD가 달라지는 것은 재개 시 실제 commit의 파일 목록·부모를 확인해 대조한다. 파일에 자기 commit hash를 넣으려고 무한히 재commit하지 않는다. 게시 후 receipt만 달라졌다면 그것 때문에 추가 push를 만들지 않는다.

## 중단·예외 처리

- 인증/접근 실패, remote 불명확, 잘못된 브랜치, 예상하지 못한 staging, 원격 분기 충돌, 검증 부족이면 자동 게시를 중단한다. 결과와 필요한 조치를 handoff에 남기고 알려준다.
- 사용자 로그인이나 계정 변경, 자동 인증정보 이전, 자동 force push·reset·rebase·merge로 해결하지 않는다. 원격 기존 작업을 덮어쓰지 않는다.
- 동일 결과가 이미 게시되어 변경이 없으면 빈 commit이나 중복 push를 만들지 않는다. 빌드·조사 프로세스가 실행 중이면 상태와 출력 위치만 기록하고 중복 실행하지 않는다.
- 샌드박스·네트워크의 실행 승인 요구는 사용자 게시 정책과 별개다. 환경이 거부하면 우회하지 않고 로컬 결과를 보존한다.

## 현재 프로젝트 제한

Gazebo/World::step/Stage B 실행, production Physics/SDF 및 시스템 패키지·라이브러리 변경, 전역 loader 변경, 기존 evidence·Capture Validity·Clock 기준·solver 알고리즘 변경은 금지한다. **Stage B BLOCKED / NOT_RUNTIME_VERIFIED**를 유지한다. 이 문서의 자동 게시 승인은 Host 실행이나 main 병합 승인이 아니다.
