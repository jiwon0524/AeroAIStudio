# Gazebo integration V0.5

Target: Ubuntu24.04, Gazebo Harmonic (gz-sim8), optional ROS2 Jazzy. The generator uses no map provider APIs and can later accept provider-neutral ScenarioSpec data.

Implemented in `gazebo/`:

- diagnostics: bounded CLI probes for `gz sim --versions`, ROS2 and `ros_gz_bridge`, plus Python/PyTorch/CUDA/GPU information;
- GazeboWorldGenerator: actual SDF1.9 XML, ground plane, directional light, physics/user-command/scene-broadcaster systems, boundary walls, box obstacles and colored goal/agent/zone markers;
- GazeboEnvironment: real `gz sim -r world.sdf` process launch (or `-s` server mode), log file, PID/exit status and owned-process shutdown. UI polls process state. It never substitutes a GridWorld as a fake 3D simulator;
- GazeboSensorProvider Protocol: start/stop/latest Observation/status for future Camera/Depth/LiDAR/IMU/GPS/Range implementations;
- RosGazeboBridgeManager: availability check, explicit `parameter_bridge` topic mappings, start/stop/status/list_topics.

**V0.5 is world launch integration, not a 3D training/control loop.** reset/step/live observation explicitly raise NotImplementedError rather than returning invented physics or sensor data. Capabilities describe the target engine's features; `training_available=False` describes this adapter's current scope. Gazebo selection cannot start Trainer; it routes to world launch with an explanation.

Moving objects are orange **static proxies in SDF**. Their 2D Grid motion is not yet reproduced by a Gazebo plugin. Scenario metadata preserves their movement for V0.6. Danger/Slow markers do not yet impose Gazebo physics/reward rules. Cell size is1m; grid(x,y) maps to world(x+.5,y+.5). This is an explicit project coordinate convention, not an ENU/vehicle frame assertion.

## App flow

Scenario Lab → Export to Gazebo → generated_worlds/aero_<hash>/world.sdf + metadata.json → Launch Gazebo. Diagnostics also has Export/Launch/Stop. The generated world is standalone and uses no external Fuel asset download. SDF XML is staged and parsed before replace. On missing Gazebo, the app displays Unavailable and continues to provide GridWorld, Training, Replay and Models.

Generated process log: the world directory's gazebo.log. `Running` means only that the process is alive. It is **not proof that a frame rendered**. Check the actual Gazebo window and log on Ubuntu. Runtime compatibility with Ionic/Jetty is not claimed from SDF generation alone.

## Ubuntu smoke

Install the Harmonic binaries using the official installation instructions. Source the ROS Jazzy environment only if testing the optional bridge. Install this existing Python project in a virtual environment, then:

```text
python tools/gazebo_smoke.py --output ./work/gazebo-smoke --gui
gz sim -r ./work/gazebo-smoke/generated_worlds/<generated-id>/world.sdf
```

The smoke tool also attempts `gz sdf -k` when gz is present, launches for3 seconds and records process status. It does not auto-certify visual rendering. Our current Windows environment has no gz/ros2/bridge, so only XML generation/structure and graceful-unavailable behavior were verified. **No actual Gazebo launch or render was performed here.**

## V0.6 work

Implement GazeboSensorProvider backed by timestamped transport/ros_gz samples, clock/step barriers with finite timeouts, reset/entity lifecycle, action/observation codecs, 2D projection + 3D pose snapshots and renderer selection. Add dynamic movement plugins, true agent entity control and scenario semantics, then run the common Agent→SimulationEnvironment→Brain/Replay loop. Run Ubuntu CI with real physics/sensor services. Bit-for-bit Grid checkpoint determinism does not imply deterministic Gazebo physics.
