# Aero AI Studio V0.6

기존 V0.5 프로젝트를 같은 폴더에서 확장했습니다. 기존38개 테스트와 데이터 경로를 보존하고 Reward V2·Safety·동적 예측·Curriculum·Double DQN·Trajectory 및 native Gazebo closed-loop 경로를 추가했습니다.

**현재 Windows에서는 Gazebo 실제 실행이 NOT VERIFIED입니다.** Gazebo를 GridWorld로 대체해 실행했다고 보고하지 않습니다. GridWorld 학습·평가는 실제 실행했고, Gazebo의 서비스/센서/stepping 계약은 전송fixture 단위 테스트와 Ubuntu용 별도 integration test로 구분합니다.

## 실행

현재 `.venv`에는 PySide6·pytest·CPU PyTorch·NumPy가 설치되어 있습니다.

```powershell
.\Start.ps1
.\.venv\Scripts\python.exe -m pytest -q
```

새 설치: `Setup.ps1` 또는 DQN을 포함하는 `Setup.ps1 -IncludeDqn`. Linux에서는 Python3.11+의 venv에서 `python -m pip install -e ".[dev,dqn]"` 후 `python -m aero_ai_studio`를 실행합니다. Ubuntu Harmonic native bindings는 Ubuntu의 system Python/`--system-site-packages` venv가 필요합니다. 설치 명령 안내는 scripts/setup_ubuntu_sim.sh이며 자동 시스템 변경을 실행하지 않습니다.

## 사용 흐름

1. 기존 프로젝트를 열고 Scenario를 저장합니다. 기존 Basic/Local/Sensor 설정, Map Editor, 모델·Replay·Paper/Video UI는 유지합니다.
2. Training에서 Q-Learning/DQN, Observation, Q encoder(auto/basic/compact/canonical), Simulator를 선택합니다. 기본 legacy reward/Safety OFF/Curriculum OFF/Double DQN OFF는 기존 동작을 보존합니다.
3. 선택적으로 Reward=v2, Safety, Double DQN, replay warm-up, Curriculum과 승급 threshold를 켭니다. Double DQN은 online argmax의 target value를 사용합니다. 기존 Huber/gradient clipping/target sync는 유지합니다. Reward clipping은 API TrainingConfig에서 지정할 수 있습니다.
4. Train/Stop/Save Checkpoint/Resume을 사용합니다. Stage·RNG·epsilon·buffer/optimizer/target 등 필요한 상태가 복원됩니다. Simulator 선택도 config에 저장되어 재개 시 backend가 바뀌지 않습니다.
5. Evaluation에서 Static Known/Static Unseen/Dynamic Easy/Normal/Hard/Gazebo Static을 선택합니다. 별도 **Evaluation Safety Layer**로 같은 정책의 OFF/ON을 비교합니다. seed는 학습과 분리합니다.
6. Replay/Brain Map V4에서 proposed action, Safety 개입·최종 action, 센서 prediction/TTC, reward breakdown과 결과를 확인합니다. Observation Debug는 정책 입력과 debug world를 구분합니다.
7. Trajectory 페이지는 전체 경로·목표·장애물·충돌점 및 현재 step cursor를 표시합니다. Gazebo pose가 있는 로그도 동일한 top-down projection으로 표시합니다. 실제3D Gazebo 재생을 의미하지 않습니다.

## Gazebo 실행 경로

Ubuntu24.04/Harmonic을 대상으로 구현했습니다. Headless/GUI 선택, SDF Export, 비동기 Launch/Stop, Run3D Closed Loop, 또는 Training의 Gazebo backend를 사용합니다. Closed Loop 버튼은 저장된 BASIC/SENSOR 모델을 선택한 뒤 실제 Evaluator를 실행합니다. Rule smoke는 tools/closed_loop_smoke.py를 사용합니다.

Process alive뿐 아니라 native scene service에서 agent entity pose를 확인하고, fixed simulation stepping 뒤 새 LaserScan timestamp를 요구합니다. GUI가 그려졌다는 주장은 별도입니다. Native transport/sample은 timeout을 가지며 Qt thread에서 polling/wait를 수행하지 않습니다. GridWorld는 Gazebo 설치와 무관하게 실행됩니다.

제어는 단순 box entity의 **kinematic set_pose**입니다. 비행·모터·PX4·Offboard·실기체는 없습니다. Collision은 전방 실제 ray의 swept-command clearance 및 실제 pose/경계/동적 entity 근접 검사이며 물리 contact sensor로 검증된 충돌이 아닙니다. Gazebo hard-reset·step·센서 freshness는 실제 Ubuntu에서 검증해야 합니다.

## 알려진 한계

- 실제 Gazebo/Ubuntu runtime에 접근할 수 없어 launch/world/entity/sensor/movement/reset/clean-shutdown은 **NOT VERIFIED**입니다. 기존 WSL distro 목록도 비어 있었습니다. Real integration test는 skip되었습니다.
- Native bindings 기준은 gz.transport13/gz.msgs10입니다. Ionic/Jetty나 다른 Python ABI는 검증하지 않았습니다. Headless GPU LiDAR도 Ogre2/EGL rendering capability가 필요합니다.
- Gazebo는 kinematic pose 이동이며 physics dynamics가 아닙니다. 장애물 관통/센서/서비스 순서의 실환경 통합 검증이 필요합니다. 모델 action과 실제 관측pose가 다르면 오류로 중단합니다.
- Gazebo range는 실제4-ray scan을 요구합니다. Camera/pointcloud/LOCAL occupancy mapper·moving identification/TTC는 미구현이며 unknown을 반환합니다. 가짜 센서를 대입하지 않습니다.
- Grid prediction은 선형 추정이고 random turn/bounce를 예견하지 못합니다. Safety에도 잔여 충돌과 Timeout이 있습니다. Canonical/Reward/Safety 세부사항은 별도 문서를 참고하세요.
- Curriculum static stage는 알려진 고정 geometry에서 새 seed 평가입니다. 승급 성공은 unseen-map 일반화 증거가 아닙니다. 평가best checkpoint 자동 Registry 선택은 아직 없습니다.
- Minimum clearance는 경계를 포함하며 출발 시 경계 부근0.3m가 최소로 남는 경우가 많습니다. 성공률만큼이나 한계와 함께 해석해야 합니다.
- JSON/모델 checkpoint와 trajectory prefix 저장은 대규모 run에서 공간/I/O 부담이 있습니다. 여러 앱의 동시 workspace 쓰기·Gazebo log retention·강제 종료 복구 확장은 후속 과제입니다.
- Native Windows 수동 E2E와 Linux UI는 미검증입니다. Paper/Video/지도·다른 simulator는 확장하지 않았습니다.
